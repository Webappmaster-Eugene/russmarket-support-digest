# Развёртывание

Compose содержит приложение и PostgreSQL 16. У PostgreSQL есть именованный
том и внутренняя сеть, а приложение подключается под ролью `desk`.
Перед запуском сервер применяет SQL-миграции, проверяет учётные записи
и добавляет четыре учебных случая при первом запуске.

## Переменные окружения

В настройках Dokploy или в локальном файле `.env` задайте:

- `APP_ORIGIN` — адрес приложения, включая схему. Для локального Compose
  используйте `http://127.0.0.1:4367`.
- `POSTGRES_PASSWORD` и `DESK_DB_PASSWORD` — раздельные случайные секреты.
  Для Compose используйте шестнадцатеричные строки, чтобы они корректно
  вставлялись в URI подключения.
- `REVIEWER_PASSWORD_HASH` и `SUPPORT_PASSWORD_HASH` — хеши двух разных
  паролей. Оба логина дают доступ на чтение и запись в общий кабинет.
  После `pnpm db:build` команда
  `node .build/bootstrap.cjs --hash-password` читает пароль со стандартного
  ввода и печатает его хеш. Используйте случайные пароли от 16 символов.
  Изменение хеша при перевыкате завершает сессии этого логина.

Локальный вариант запуска с опубликованными только на loopback портами:

```sh
docker compose -f compose.yaml -f compose.local.yaml up --build --wait
```

Для разработки без контейнера приложения задайте `DATABASE_URL` в локальном
окружении, запустите PostgreSQL и выполните `pnpm db:setup`, затем
`pnpm dev`. Настройте `APP_ORIGIN` на фактический адрес разработки.

## Обновление с двух пространств

Перед обновлением проверьте наличие восстанавливаемой копии PostgreSQL.
На старте `002_shared_workspace.sql` переносит случаи, переписку и снимки
из `review` в `support` в одной транзакции. UUID, версии карточек и архив
сохраняются. Оба логина и существующие сессии получают доступ к объединённым
данным. При совпадении ID остановитесь и сверьте записи по CRM до повтора
миграции. Для возврата к версии с двумя пространствами потребуется
предмиграционная копия базы.

## Эксплуатация

Для хоста используйте HTTPS и маршрут Dokploy к порту 3000. Настройте
ежедневный `pg_dump` в отдельное хранилище резервных копий. Проверяйте
восстановление в одноразовой БД. При проверке доступности используйте
`/api/health` и вход под обоими логинами. Резервные копии с рабочими данными
храните с теми же ограничениями доступа, что и исходную БД.
