# Сводка поддержки

Демо ежедневной сводки по CRM и рабочим чатам. На главной странице открывается
очередь из четырёх случаев. В разделе «Данные» можно изменить пример, добавить
синтетический случай и пересчитать сводку.

## 1. Как собирается сводка

Сервер принимает снимок CRM и сообщения, сопоставленные по ID случая, проверяет
входные данные и применяет правила к каждому случаю на момент расчёта.

- Для оформления проверяет дату первого выхода и статус документов. Для
  увольнения проверяет последний рабочий день и наличие подтверждения руководителя.
  Просроченное подтверждение требует вмешательства, срок сегодня требует проверки сегодня.
- Для доставки сверяет время расчёта со сроком в CRM. Открытая доставка в момент
  наступления срока уже требует вмешательства. Подтверждённая в CRM приёмка
  закрывает вопрос в рамках этой сводки.
- Сохраняет авторство сообщения и отдельно показывает, что оно добавляет к CRM.
  Из фраз курьера «приеду к 13:00» и «раньше 13:00 не приеду» извлекает только
  однозначную оценку времени на день сводки. Если время неясно, предлагает уточнить
  его у курьера. Оценка позже срока поднимает приоритет до проверки сегодня.
- Выводит срочные случаи первыми. Внутри одного приоритета ближайший срок идёт
  раньше, а при равных сроках сохраняется порядок входных данных.

Интерфейс отправляет данные в `POST /api/digest`. Модуль `src/digest/`
вычисляет результат локально. В демо записи из CRM и чатов вводятся вручную
и остаются в памяти текущего запроса и открытой страницы. Журналы содержат
технические сведения о работе сервера.

## 2. Сводка на понедельник, 10:00 МСК

Начать с **П-08**, поскольку срок доставки уже наступил. В тот же день получить
подтверждение по **С-24**, затем проверить документы по **С-17** до первого выхода.

| Случай | Запись CRM | Только из чата | Что проверить и сделать |
| --- | --- | --- | --- |
| **П-08 · Вмешаться сейчас** | Доставка до 10:00, карты в пути. | Курьер сообщает, что раньше 13:00 не приедет. | Уточнить актуальное время у курьера, предупредить точку и согласовать, кто подтвердит приёмку. |
| **С-24 · Проверить сегодня** | Последний рабочий день сегодня, подтверждения руководителя нет. | Сотрудник говорит, что руководитель в курсе. | Получить явное подтверждение руководителя и зафиксировать его в CRM. Если ответа нет, эскалировать по регламенту. |
| **С-17 · Проверить до выхода** | Первый выход завтра, документы ожидаются. | Сотрудник сообщает, что вчера отправил фото документов руководителю. | Проверить у руководителя получение и комплектность. Обновить CRM по итогам, при необходимости согласовать передачу через рабочий канал. |
| **П-09 · Без действий** | Статус «Принято», приёмка подтверждена в 09:20. | Получатель сообщает о приёмке и проверке количества. | Оставить в сводке для сведения. |

## 3. Первый запуск

На пилоте в 10:00 МСК импортируем разрешённые выгрузки из CRM и сообщения из
согласованных рабочих чатов, связывая их по ID случая. Сотрудник поддержки откроет
сводку в браузере перед разбором очереди. Перед действием он сверит статус и срок
с карточкой CRM, а сообщения и неоднозначные оценки уточнит у ответственных.
Пять рабочих дней команда будет параллельно вести ручную сводку и отмечать время
подготовки, пропущенные срочные случаи и лишние эскалации. По итогам сравним
медианное время, разберём каждое расхождение с командой и согласуем правила
перед ежедневным использованием.

## Запуск и проверка

Понадобится Node.js 22 и Corepack. Ключи и переменные окружения для приложения
не нужны.

```sh
corepack enable
pnpm install --frozen-lockfile
pnpm dev
```

Откройте `http://localhost:3000`. Пример запроса и поля описаны в [документации API](docs/api.md).

```sh
pnpm smoke
pnpm exec playwright install chromium
pnpm test:e2e
```

Production-образ запускается тем же сервером для страницы и API.

```sh
docker build -t support-digest:local .
docker run --rm -p 127.0.0.1:3000:3000 support-digest:local
```

В `compose.yaml` подготовлен сервис `app` для выката за прокси. Docker
проверяет готовность по `GET /api/health`.

### Что проверено на практике

- В 12 тестах правил и API проверены четыре исходных случая, граница 10:00,
  часовые пояса, неоднозначная оценка курьера, подтверждения, повторяющиеся ID
  и ошибки входных данных.
- В четырёх сценариях Playwright проверены открытие сводки и каждого источника,
  добавление и удаление своего случая, ошибки формы, копирование и экран 320 px.
  Сценарии прошли на запущенном production-образе Docker.
- Линтер, проверка типов, production-сборка и аудит рабочих зависимостей прошли.
- В пилоте предстоит проверить сопоставление записей на реальных выгрузках,
  полноту случаев и выигрыш во времени по сравнению с ручной сводкой.
