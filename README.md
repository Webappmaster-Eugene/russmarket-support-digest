# Сводка поддержки

Рабочий кабинет для сотрудников, которые сверяют оформления, увольнения и
доставку карт со сведениями из CRM и рабочих чатов. Сводка отвечает на три
вопроса: с чего начать, что проверить и какое действие выполнить.

## Как работать

1. Войдите с выданными логином и паролем. Проверяющим выдаётся доступ
   `reviewer`, сотрудникам поддержки — `support`.
2. Нажмите **«Новый случай»** в верхней навигации. Выберите тип, заполните ID и
   сведения из CRM. Сохраните случай и при необходимости добавьте сообщения в
   карточке, указывая автора и время по Москве.
3. Откройте **«Сводка»**. Верхние показатели показывают срочность, список
   упорядочен по приоритету и сроку. По ссылке из списка откроется карточка,
   где раздельно полями видны CRM, переписка и следующий шаг.
4. При расхождении проверьте факты, исправьте запись CRM в карточке при
   необходимости и сохраните пояснение к сообщению. Закрытые случаи можно
   перенести в архив и восстановить из него.
5. **«Сохранить сводку»** создаёт снимок, который можно найти в **«История»** и
   скопировать. В проверочном пространстве здесь уже лежит исходная сводка
   на понедельник, 10:00 по Москве.

Проверяющий работает с отдельным набором учебных данных. Для проверки
формы используйте вымышленные случаи и сообщения.

## Сводка по заданию

| Случай | CRM | Из переписки | Решение |
| --- | --- | --- | --- |
| **П-08** | Карты в пути, срок 10:00. | Курьер прибудет не раньше 13:00. | Начать с этого случая: уточнить время, предупредить точку и договориться о подтверждении приёмки. |
| **С-24** | Последний день сегодня, согласования нет. | По словам сотрудника, руководитель в курсе. | Сегодня получить явное подтверждение и внести в CRM. |
| **С-17** | Выход завтра, документы ожидаются. | Сотрудник сообщил об отправке фотографий. | До выхода уточнить получение и комплектность у руководителя. |
| **П-09** | Приёмка подтверждена в 09:20. | Получатель сообщил о приёмке и проверке количества. | Оставить для сведения. |

Сервер применяет правила к сохранённым данным и времени отчёта. Чат сам по
себе не меняет CRM. Если получатель после приёмки явно сообщает, что карты
ещё не получены, сводка поднимает приоритет. Остальные расхождения оператор
может отметить сам. Из однозначной фразы курьера сервер извлекает оценку
на день сообщения и сравнивает её со сроком. Неоднозначное время выводится
как вопрос для ручной сверки.

## Первый запуск

На пилоте операторы заносят сведения из разрешённых систем через форму.
Изначально в проверочном пространстве разыгрывают четыре учебных случая.
Сотрудник сверяет срочные строки с CRM и уточняет спорные сообщения перед
действием. Пять рабочих дней команда ведёт ручную и автоматическую сводки
параллельно, отмечая время подготовки, пропущенные срочные случаи и лишние
эскалации. По итогам сравнивают медианное время и разбирают расхождения
до перехода на ежедневное использование.

## Архитектура

Next.js и React обслуживают интерфейс и API. Модуль `src/digest` рассчитывает
приоритет из переданного времени и случаев. Модуль `src/server` проверяет
доступ и хранит данные в PostgreSQL. Записи имеют версию, поэтому сохранение
устаревшей формы не перезапишет чужую правку. Снимок хранит готовый результат
и не меняется при последующей редактуре случая.

## Запуск и проверки

Локально на Docker Compose прошли 12 тестов правил и валидации, 4 теста
интеграции с PostgreSQL и 5 сценариев в Chromium. Проверены сохранение
после пересоздания контейнеров и восстановление копии в отдельной БД.
Аудит зависимостей не показал известных уязвимостей. В пилоте предстоит
измерить выигрыш во времени и проверить решения на реальных случаях.

Нужны Node.js 22, Corepack и Docker Compose. Для полного одноразового прогона
создаётся отдельная БД. Используются локальные порты 4367 и 55448.

```sh
corepack enable
pnpm install --frozen-lockfile
sh scripts/verify-local.sh
```

Для разработки и выката см. [инструкцию по развёртыванию](docs/deployment.md).
Контракт защищённых маршрутов описан в [API](docs/api.md).
